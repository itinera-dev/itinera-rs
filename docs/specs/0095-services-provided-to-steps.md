# 0095: Services provided to steps

Tech spec for [proposal 0095](https://github.com/itinera-dev/spec/issues/95), implemented in [#103](https://github.com/itinera-dev/itinera-rs/issues/103) as stage 10 of the [tier 1 plan](../tier-1-plan.md), which holds what crosses proposals. It amends [0002](0002-foundations.md), [0003](0003-rescue-steps.md), [0011](0011-events.md) and [0042](0042-configuration-errors-before-the-journey.md). Proposal [0102](0102-global-metadata.md) amends it, and its tech spec covers how a service provider sets global metadata through its reporter. Proposal [0104](0104-service-implementation-on-events.md) amends it too, and its tech spec covers what a provider returns, a `Provided<T>` made with `provide!`, and the implementation and data that `service_provided` carries.

Status: done.

## API

Everything below is in `itinera::service`, unless another module is named.

- **`Service<T: ?Sized>`**, a typed token holding a key, declared as a constant like `Input<T>`: `const PAYMENTS: Service<dyn PaymentGateway> = Service::new("payments");`. `T` should be a trait object, such as `dyn PaymentGateway`, so that a step depends on what a service can do. Rust has no bound that holds only for trait objects, so the token accepts any `Send + Sync + 'static` type; `#[service]` enforces it.
- **The step's side.** `StepNeeds::service(&PAYMENTS)` declares a service, and `Resolved::service(&PAYMENTS)` takes it, as `Result<&'a T, Error>`, where `'a` is the attempt. A step may take a service more than once. Taking one it did not declare, or as another type, fails. A rescue step does the same with `RescueNeeds::service(&PAYMENTS)` and `RescueResolved::service(&PAYMENTS)`.
- **`ProviderName`**, a `&'static str` newtype like `AdapterName`.
- **The scopes** `PerJourney` and `PerAttempt` are types, and implement the sealed trait `ProviderScope`, whose sealing trait tells the executor which scope it is, so a descriptor does not store it.
- **`ServiceProviderDescriptor<W, S: ProviderScope, M = Synchronous>`** describes a provider:
  - `::new(name, &TOKEN, provide)` makes one of scope `PerJourney`, and `::per_attempt(name, &TOKEN, provide)` one of scope `PerAttempt`. With the `async` feature, an asynchronous workflow's providers are made with `::new_async` and `::per_attempt_async`, which take an `async fn` as well as a function returning a future (`AsyncProvide`);
  - `provide` is a function of the workflow's own value and a `Requested<'_, W, Provider<S>, M>`, returning `Result<Provided<T>, Error>`, usually a method of the workflow;
  - `.needing(HookNeeds<Provider<S>>)` declares its requests, and `.step(name)` attaches it to a step. `.name()` gives its name.
- **`Provider<S>`** is the hook kind of a provider. `Requested` gives it the journey ID, data from the workflow and a reporter. One of scope `PerAttempt` also has `step_name()` and `attempt()`.
- **`itinera::policy::ReportingHookKind`**, a trait every policy hook kind and `Provider<S>` implement, carries `HookNeeds::reporter()` and `Requested::reporter()`. Two inherent `reporter` methods on overlapping impls would break type inference in existing code.
- **`WorkflowBuilder::provider(descriptor)`** declares a provider on the workflow. The descriptor's mode is the workflow's, so a synchronous workflow cannot be given an asynchronous provider.
- **The listing.** `ListedStep::services` lists the services each step requests, as `ListedService { key, provider }`, in the order the step declares them.
- **Events.** `EventBody::ServiceProvided` and `EventBody::ServiceProviderFailed` carry the step's attempt, the key and the provider; since 0104, `ServiceProvided` also carries the implementation and the provider's data. `HookSource::Provider` names the provider and the step's attempt, for its `journey_*` events, and, within `RequestSource::Hook`, for its requests. `event::Requester::Provider` and `journey::Requester::Provider` name it in aborts. `JourneyAbort::StepCouldNotBeBuilt` names the provider when a provider failed, with `Supplier::Provider`.
- **Violations.** `ServiceNotProvided`, `ServiceRequestedTwice`, `ServiceProvidedTwice`, `DuplicateProviderName`, `ServiceProviderForUnknownStep` and `WrongServiceType`, with a `ViolationKind` of each.
- **`DescribedStep::SERVICES`**, the keys of the services a step requests, in the order it declares them, empty unless an implementation says otherwise. `#[step]` fills it, for the compile-time check that every service is provided.

## Macros

The macros of [section 11 of the plan](../tier-1-plan.md#11-macros) declare services and providers too.

- **`#[service]`** marks a parameter of a step's `run` or `new`: `#[service("payments")] gateway: &dyn PaymentGateway`, keyed by the parameter's name when no key is written. It takes the service by shared reference, as a trait object, possibly in parentheses with its bounds or borrowed for a named lifetime, and refuses a concrete type, which the builder cannot refuse. It generates `StepNeeds::service` and `Resolved::service` with a token of the written type, so the reference is borrowed for the attempt. The services of `new` are declared with its inputs, in `FromInputs::needs`, and those only `run` takes after its handles. A key that `new` and `run` both take is declared once, and a generated `PhantomData` assignment makes both types the same. It marks a parameter of a rescue step's `run` the same way, under `#[rescue_step]`, which generates `RescueNeeds::service` and `RescueResolved::service`, declared after the rescue step's handles; a rescue step has no `new`.
- **`#[provider]`** marks a method of the workflow's `impl` block: `#[provider]` for journey scope and `#[provider(per_attempt)]` for attempt scope, with `steps = [...]`, `key = "..."` and `name = "..."`, each optional; the key and the name are the method's otherwise. The method takes `&self`, returns `Result<Provided<T>, Error>`, and requests `#[from_workflow]` and, recognised by their types with no mark, `&JourneyId` and a reporter, and, of attempt scope, `StepName` and `Attempt`. `#[workflow]` generates a hidden associated function of the workflow per provider and mode, which resolves the requests and calls the method, so that `T` is inferred from the written return type, and declares a `ServiceProviderDescriptor` of it with `WorkflowBuilder::provider`.
- **The mode.** The `impl` block's expansion does not know the workflow's mode, so it implements a hidden trait, generic over the mode, for each mode its providers fit: `Synchronous` when every provider is synchronous, and `Asynchronous`, with the `async` feature, unless a synchronous provider requests a reporter, whose type is the synchronous one. A synchronous provider in an asynchronous workflow is wrapped in an `async fn`. The struct's expansion requires that trait for its mode, so a provider of the other mode is a compile error, with a message from `#[diagnostic::on_unimplemented]`.
- **Compile-time checks across the two expansions.** The `impl` block lists its providers' keys and steps in a hidden associated constant; the struct's expansion checks, for each step it lists, in a constant evaluated as the program compiles, that every key of its `DescribedStep::SERVICES` is served, and names the first one that is not. It checks each rescue step it gives a step the same way, against `DescribedRescueStep::SERVICES`, and names the rescue step by the name the engine gives it, the step's followed by `_rescue`, which, since 0098, providers may be attached to. Both constants are hidden.
- **The service's type, through generated bounds.** A key is also written as a type, the nested tuple of its characters as `itinera::service::Char<const C: char>`, ending with `()`, which both expansions spell the same from the literal. For each key, the `impl` block implements the hidden marker trait `ProvidesService<Key, T>` for the workflow: for the one `T` its providers make, when every provider of that key writes its return type as `Result<Provided<T>, ...>` or `Result<Provided<T>>` with `T` written alike, and otherwise for every `T`. `#[step]` gives the step a hidden function, `__itinera_services_fit::<W>()`, bounded by `W: ProvidesService<Key, T>` for each service it takes, and `#[rescue_step]` gives a rescue step the same. The struct's expansion names that function with the workflow for each step it lists and each rescue step it gives one, so a service requested as another type is a compile error at the step's name or the rescue step's type, with a message from `#[diagnostic::on_unimplemented]`; a step or rescue step the macros did not describe resolves the name to a local trait's empty default. For a rescue step the bound is exact too: the implementation names one `T` only when every provider of the key makes it, the one serving the rescue step among them. A block that could not be read implements `ProvidesService` for every key and type, so that its error stands alone. The trait takes `T` as a parameter rather than naming it in an associated type, since an associated type of an implementation must be as visible as the implementation, so a workflow more visible than its service's trait would not compile. These items live in `itinera-core/src/service/fit.rs`, hidden.

## How the rules are enforced

| Rule | Enforced by |
|---|---|
| Only steps request services | types: only `StepNeeds` and `RescueNeeds` have `service`; hooks and adapters have no way to request one |
| A service is requested by key and type, and is always required | types: `Service<T>` carries both; `Resolved::service` returns `Result<&T, Error>`, failing only for a service the step did not declare |
| Which provider serves a step: the one of that key attached to it, else the one attached to no step | `serving` in `service/descriptor/entry.rs`, used by admission, the listing and the engine alike |
| `service not provided`, `service requested twice`, `service provided twice`, `duplicate provider name`, `service provider for unknown step`, `wrong service type` | `build()`, in `workflow/violation/admission/services.rs`, and, for what each step and rescue step requests, in `workflow/violation/admission/services/requests.rs`; the type is compared by the `TypeId` of `Box<T>` |
| `service not provided`, in a workflow the macros declare | a compile error: a constant check in `itinera-macros/src/workflow/services.rs`, with its functions in `services/functions.rs`, against the keys `#[step]` lists in `DescribedStep::SERVICES` and `#[rescue_step]` in `DescribedRescueStep::SERVICES` |
| `service requested twice`, by the macros | a compile error when one function takes a key twice, a rescue step's `run` among them, in `itinera-macros/src/step/service.rs`; a key that `new` and `run` both take is declared once |
| `service provided twice`, `duplicate provider name`, by the macros | a compile error, in `itinera-macros/src/workflow/parts/provided.rs`, as is a provider listing a step twice or an empty `steps = []` |
| `service provider for unknown step`, by the macros | a compile error: a constant check in `itinera-macros/src/workflow/parts/provided.rs`, against the steps the struct lists, followed by the names of their rescue steps |
| `wrong service type`, by the macros | a compile error: the bounds of the hidden function of the step or rescue step, against what the `impl` block says the providers of each key make, from `itinera-macros/src/step/service.rs`, `itinera-macros/src/workflow/parts/provided/declaration.rs` and `itinera-macros/src/workflow/services.rs`; left to `build()` only for a key whose providers write their return types differently, or other than as `Result<Provided<T>, …>` or `Result<Provided<T>>`, for which the first call to `descriptor()` panics with the violation |
| `attempt request in journey scope`, by the macros | a compile error: a `StepName` or an `Attempt` parameter is refused without `per_attempt`, in `itinera-macros/src/workflow/parts/provider/request.rs` |
| A provider follows the executor's execution modes, by the macros | a compile error: the hidden trait of the providers' modes, in `itinera-macros/src/workflow/parts/provided/declaration.rs` |
| `attempt request in journey scope` | types: `step_name()` and `attempt()` exist only on `Requested<'_, W, Provider<PerAttempt>, M>`; see the excluded scenarios |
| A provider may request the journey ID, data from the workflow and a reporter, and nothing else | types: `HookNeeds<Provider<S>>` and `Requested<'_, W, Provider<S>, M>` offer only those, since `Provider<S>` is neither a step hook kind nor a policy hook kind |
| Services are resolved after the step's inputs, in the order the step declares them, before it is built | the engine, in `engine/attempt.rs` and `engine/services.rs` |
| Journey scope: the provider is called the first time a step it serves needs its key, and that instance is lent to every later attempt of the steps it serves | the engine keeps one `OnceLock` slot per journey-scoped provider, in `engine/services/kept.rs`, in an `Arc` the journey owns, dropped when the run ends |
| Attempt scope: the provider is called for every attempt, and its instance serves that attempt only | the engine owns the instance while the step is built and runs, and drops it when the attempt ends, in `engine/attempt.rs` |
| A provider's requests, events and failure: `optional_input_absent`, `required data missing` and `wrong type` naming it, `service_provided`, `service_provider_failed`, `step could not be built` naming it | the engine, in `engine/services.rs`, through the same request resolution and reporting as a hook's |
| A service is lent for its attempt only | types: `Resolved::service` returns a reference bound to the attempt; no conformance case checks a kept service |
| A provider's reporter is valid only during its call | types: its lifetime is the call's, as a hook's reporter is |
| A provider returns an instance or an error, never nothing | types: its function returns `Result<Provided<T>, Error>`; see the excluded scenarios |
| A provider follows the executor's execution modes | types: its mode is the workflow's; see the excluded scenarios |
| Event data a provider emits is a value | types: the reporter takes `Value`s only, as a hook's does |
| A rescue step is never served by a provider attached to the step it rescues | `serving` in `service/descriptor/entry.rs` serves a rescue step by its own name, as any step. Admission checks each rescue step's services as a step's, in `services/requests.rs`, so a service that only a provider attached to the rescued step supplies is `service not provided`. Since 0098, a provider may be attached to a rescue step's name, as its tech spec says |

### When `wrong service type` is left to `build()`

The bound compares the step's type with the one written type of every provider of the key. When the providers of one key provide types written differently in their return types, the `impl` block's expansion cannot tell whether they name the same type, nor, for a step, which of them serves it, since that depends on the steps each is attached to and the struct's expansion sees the keys only as constant values; selecting a type by attachment would need overlapping implementations, which coherence refuses. The workflow then provides such a key as any type, and `build()` checks its steps, so a workflow the macros declare with that mistake panics, naming the violation, the first time its descriptor is asked for. A return type written other than as `Result<Provided<T>, ...>` or `Result<Provided<T>>`, through an alias of another name than `Result` for instance, is left to `build()` the same way.
